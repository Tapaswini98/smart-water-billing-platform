# Backups

## What is committed here

One sanitized sample dump: `sample-<timestamp>.dump`, with a `.sha256` alongside it.

It contains the **schema plus synthetic demo data only**:

- Seed users with well-known Development passwords (`Admin#12345`, `Customer#12345`).
- Fictional customer names and addresses. No real person's data.
- Synthetic meter readings generated by the seeder, including deliberately planted
  anomalies (a duplicate, an out-of-order arrival, a meter reset, and a reporting gap)
  so that a restore can be verified against known-interesting data.
- No API keys in plaintext — only SHA-256 hashes, as in any environment.
- No production credentials, connection strings or signing keys.

This is a deliberate decision, not an oversight. The brief asks for a copy of the
backup in the repository; the repository is public. A dump with realistic personal
data or any real credential must never be committed, whatever the instruction says,
so what is committed is the version that demonstrates the restore path without
creating a disclosure.

## Everything else in this directory is ignored

`.gitignore` admits only `sample-*.dump`, its checksum and this file. Dumps produced
by `scripts/backup.sh` during normal operation stay local.

## Using it

```bash
# Verify the sample dump restores and the data is intact (no existing
# container or database is touched — a throwaway one is created and removed):
scripts/verify-restore.sh

# Restore it into the running development database (destructive):
scripts/restore.sh --file backups/sample-<timestamp>.dump --yes
```

The full backup method, schedule, RPO/RTO and disaster-recovery procedures are in
[`docs/backup-and-recovery.md`](../docs/backup-and-recovery.md).
